# 見どころ回復ハーネス

## 目的

見どころの説明文があっても、画像取得や位置推定が失敗すると座標は空になる。
以前は空配列を永久キャッシュしたため、次の来訪者でもズームできなかった。
この失敗を既存ガイドの `hotspotPlacement` に記録し、次の処理の判断材料にする。
新規テーブル・マイグレーション・常駐ジョブは追加しない。

## 実行ループ

1. 成功済み座標は再利用する。
2. 失敗後は `nextRetryAt` まで再呼び出しを抑える。
3. 次回のAPI呼び出しで再試行する。待機時間は1分、2分、4分と増え、最大1時間。
4. 座標の範囲・必要フィールド・見どころラベルとの対応を検証する。
5. 1点以上配置できたら `ready`、できなければ `retry_wait` として結果を記録する。

保存する文脈は取得方式のバージョン、元画像URL、試行回数・時刻、次回試行時刻、
要求点数・配置点数、失敗段階（image / vision / coordinates）と機械判定用コード。
画像が変わるか取得方式のバージョンが変わると、その条件で試し直す。
古い空配列には期限がないため、初回の呼び出しで再取得する。

Wikimedia画像の取得では、公式方針に従うアプリ識別用User-Agentを付ける。
https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_User-Agent_Policy

## 検証

- テストで「失敗→失敗記録→期限前の抑制→期限後の再試行→成功記録」を通す。
- 段階別の失敗コード、画像変更時の再取得、待機時間の上限を確認する。
- stagingの実APIで返る座標と、ガイドに保存されたhotspotPlacementを照合する。

これは呼び出し時の回復処理であり、閲覧中の自動ポーリングではない。
複数リクエストの排他制御や厳密な利用予算の管理も行わない。
範囲検証は画像内の対象物への意味的な正確さまでは保証しない。
部分的な成功の場合、配置できなかった見どころは引き続き説明文のみになる。

## 今回のstaging観測

オランピアでは、古い `hotspotMarks: []` が永久に再利用されていた。
回復ループを通すとまず画像取得のHTTP 403が判明し、Wikimedia向けの
アプリ識別ヘッダー追加後は画像認識段階まで進んだ。
ただしWorkers AIはモデルのライセンス未同意（5016）で停止し、NVIDIAも403/410で利用できなかった。
この状態で座標を作ったことにはせず、`vision / provider_unavailable` と次回試行時刻を保存する。

ライセンスの同意はアプリが自動で代行しない。管理者が条件を確認して同意した後、
再試行期限を過ぎてから見どころAPIを呼び、座標取得・実画面のズームを再検証する。
公式手順: https://developers.cloudflare.com/workers-ai/models/llama-3.2-11b-vision-instruct/
